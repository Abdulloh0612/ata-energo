# РОЛЬ И ЗАДАЧА

Ты старший full-stack инженер. Построй с нуля (или доработай, если код уже есть) CRM с мониторингом для компании, которая закупает у разных производителей солнечные панели, батареи и инверторы (Deye, Eybond/Solar of Things и другие), устанавливает их клиентам и отслеживает работу оборудования через облачные API производителей.

Если в репозитории уже есть код: сначала изучи его, сохрани работающее, остальное переделай по этому ТЗ. Никаких заглушек, мёртвых кнопок, TODO и фейковых данных вне mock-режима. Язык интерфейса: русский. Все даты показывай в часовом поясе объекта.

Визуальный эталон: приложенный файл `crm-design-reference.html`. Открой его до начала работы. Токены, размеры, плотность и вид компонентов бери оттуда, все страницы должны выглядеть его продолжением.

# СТЕК (если проект пустой; иначе сохрани существующий)

- Next.js (App Router) + TypeScript (strict), монолит: UI и серверные обработчики в одном репозитории.
- Tailwind CSS + shadcn/ui, стилизованные под токены эталона. Иконки lucide-react. Шрифт Inter.
- Таблицы: TanStack Table. Графики: Recharts. Формы: React Hook Form + Zod. Состояние фильтров в URL (nuqs или searchParams).
- PostgreSQL + Drizzle ORM (миграции в репозитории). Снимки телеметрии в отдельных таблицах с индексом (object_id, time DESC) и политикой очистки по сроку хранения.
- Аутентификация: сессии на httpOnly cookie (Auth.js или better-auth), пароли argon2id.
- Фоновые задачи: pg-boss (очередь на Postgres, без отдельного Redis). Воркер запускается отдельным процессом.
- Шифрование секретов: Node crypto, AES-256-GCM. Тесты: Vitest (юнит, парсеры на фикстурах) и Playwright (ключевые сценарии, проверка ролей).
- Docker Compose: приложение, воркер, Postgres. `.env.example` без реальных значений. README с запуском за 5 минут.

# ПРЕДМЕТНАЯ ОБЛАСТЬ

Клиент → Объект (станция) → Оборудование → Показания и Аварии.
- Клиент (CRM): физлицо или компания, может иметь объекты у разных провайдеров.
- Объект: место установки (адрес, координаты, тип, мощность, часовой пояс). Привязан к одному клиенту и одному провайдеру.
- Оборудование: инвертор, батарея, логгер, счётчик и т.д.
- Провайдер: производитель с облачным API. Новые подключаются без переписывания системы.
- Заявки, задачи, документы и заметки живут только в CRM.

**Правило: у каждого клиента, объекта и единицы оборудования виден провайдер (бейдж), и по нему есть фильтр на всех списках.** У клиента с объектами у нескольких провайдеров несколько бейджей.

# РОЛИ И РАЗРЕШЕНИЯ

Роли: Администратор, Руководитель, Менеджер, Техник, Наблюдатель. Можно создавать и копировать свои, системные не удаляются. Права по модулям и действиям (просмотр, создание, редактирование, удаление, экспорт, назначение) + «только свои записи».

| Модуль | Админ | Руков. | Менеджер | Техник | Наблюд. |
|---|---|---|---|---|---|
| Клиенты | всё | без удаления | просмотр, создание, правка | просмотр | просмотр |
| Объекты и оборудование | всё | без удаления | просмотр, создание | просмотр, правка | просмотр |
| Аварии | всё | всё | просмотр | свои, обработка | просмотр |
| Заявки | всё | всё | создание, правка | свои | просмотр |
| Задачи | всё | всё | свои и созданные | свои | нет |
| Управление оборудованием (команды) | да | нет | нет | назначенные объекты | нет |
| Интеграции и ключи | да | нет | нет | нет | нет |
| Сотрудники и роли | всё | просмотр | нет | нет | нет |
| Журнал действий | да | просмотр | нет | нет | нет |
| Настройки | да | нет | нет | нет | нет |
| Экспорт | да | да | да | нет | нет |

- Страницы «Роли и права» (матрица чекбоксами) и «Сотрудники» (приглашение, смена роли, деактивация).
- Права проверяются в UI (пункты и кнопки скрыты или неактивны с подсказкой «Недостаточно прав») **и на сервере в каждом обработчике**; URL без прав ведёт на «Нет доступа».
- Опционально для роли: видит только объекты выбранных провайдеров.
- Журнал действий: кто, что, когда, над чем (вход, изменения данных, команды, изменения интеграций без значений секретов).

# АРХИТЕКТУРА ИНТЕГРАЦИЙ

**Адаптеры.** Каждый провайдер подключается адаптером с единым интерфейсом. Остальной код не знает о форматах конкретного API.
```
ProviderAdapter {
  key, capabilities{createStation, registerLogger, readConfig, sendCommands, alerts, history}
  authenticate / testConnection
  listStations, listDevices, getStationLatest, getDeviceLatest,
  getStationHistory, getDeviceHistory, listAlerts
  createStation, registerLogger, readConfig, sendCommand, getCommandResult   // по capabilities
}
```
Метод, которого у провайдера нет, не реализуется, кнопка скрывается по capabilities. Провайдеры хранятся в таблице `providers`. Администратор может добавить провайдера из интерфейса (название, адаптер, логотип, поля учётных данных).

**Секреты в БД.** Таблица `provider_credentials` (несколько записей на провайдера: разные аккаунты и регионы): provider_id, label, base_url, region, `fields_encrypted` (appId, appSecret, логин, пароль, companyId…), `token_encrypted`, token_expires_at, key_version, is_active, last_check_*, last_error.
- Шифрование на уровне приложения **AES-256-GCM**, уникальный nonce на запись. Мастер-ключ только из переменной окружения или KMS, не в БД, не в репозитории, не в логах, не в бэкапах. Ротация мастер-ключа с перешифровкой.
- Секреты не уходят на фронтенд: только маска (`••••3f2a`) и флаг «задано», ввод «только запись». Не попадают в логи, ошибки, журнал действий, заголовки авторизации маскируются.
- Доступ только с разрешением «Интеграции»; изменения пишутся в журнал без значений. Хеши паролей (у Deye SHA-256) считаются на сервере. **Вызовы к API партнёров только с бэкенда.**

**Синхронизация.** UI читает **только локальную БД**. Фоновые задачи отдельно по каждому провайдеру и аккаунту: станции и устройства каждые 15 мин и по кнопке; телеметрия каждые 5–10 мин (снимки сохраняются у нас); аварии каждые 10 мин с дедупликацией по внешнему id; история по требованию с кэшем. Ошибка одной станции или провайдера не останавливает остальных. Повторы с экспоненциальной паузой при 5xx, при 401 токен запрашивается заново. Параллелизм ограничен для каждого провайдера. Статус синхронизации виден в «Интеграциях» и в шапке. Пропавшие у провайдера объекты помечаются архивными, не удаляются.

**Привязка к клиентам.** Облака клиентов CRM не знают. Импортированные объекты получают provider_id, credential_id, external_id и пустой client_id, попадают в «Непривязанные» с подсказками совпадений (ownerName, телефон, адрес). Привязка вручную, в том числе массово, **автопривязки без подтверждения нет**. Если провайдер поддерживает createStation, объект создаётся из карточки клиента.

# ПАРСЕР И НОРМАЛИЗАЦИЯ

Вся система работает **только с канонической моделью**; названия полей провайдеров существуют только внутри его парсера.

**Конвейер:** получение → сохранение сырого ответа (`raw_payloads`, срок 14 дней) → проверка success/code, не только HTTP → парсинг (все поля необязательные, null вместо исключений, явное приведение типов) → приведение единиц (Вт, кВт·ч, В, А, °C) и времени (UTC + часовой пояс объекта) → маппинг через таблицы → валидация диапазонов (SOC 0–100, дата не в будущем, невалидное в журнал парсера) → upsert по (provider_id, credential_id, external_id), снимки добавляются. Парсер это чистая функция без сети и БД.

**Каноническая модель:**
- Site: external_id, name, address, lat, lng, site_type, grid_mode, installed_capacity_w, timezone, started_at, contact_phone, owner_name, status, raw_status.
- Device: external_id, serial_number, device_type (инвертор, микроинвертор, батарея, логгер, счётчик, прочее), model_code, model_name, parent_external_id, status, raw_status, last_data_at.
- SiteSnapshot: time, generation_w, consumption_w, grid_w, battery_w, battery_soc_pct, irradiance (любое поле может быть null; знаки мощности батареи и сети задокументируй).
- DeviceSnapshot: time + параметры `{canonical_key, value, unit, raw_key, raw_value}`.
- Alert: external_id, code, name, level (notice, warning, failure), impact (none, production, safety, both), is_open, started_at, ended_at, reason, solution.

**Таблицы соответствия в БД, редактируются из интерфейса без релиза:** `status_map`, `device_type_map`, `model_map`, `parameter_map` (raw_key → canonical_key, единицы, factor), `unit_rules`. Начальные значения грузит сид адаптера.
**Словарь параметров** канонический и расширяемый (pv_power, pv1_voltage, grid_voltage_l1, battery_soc, battery_temperature, inverter_temperature, daily_energy, total_energy…). **Неизвестные ключи не теряются**: хранятся как `unmapped`, показываются в блоке «Нераспознанные параметры», в «Интеграции → Соответствия» есть очередь с кнопкой «Сопоставить». Графики и KPI используют только канонические ключи.

**Статусы (считаются по канонической модели):**
- Оборудование: online, warning, failure, offline, maintenance (ручной флаг CRM).
- Объект: «Проблема» (нет связи ни с одним устройством или открыт failure); «Внимание» (частичная потеря связи, предупреждение, низкая выработка, низкий SOC, устаревшие данные); «Нет оборудования»; «В норме».
- Клиент: худший статус его объектов; нет объектов: «Нет объектов».
- Низкая выработка: только в дневном окне по местному времени объекта (по умолчанию 10:00–15:00); текущая генерация ниже 40% медианы дневных пиков за 14 дней (без истории: от установленной мощности). Низкий SOC: ниже 20%. Данные старше 60 минут помечаются «Данные устарели» с временем обновления. Пороги в «Настройках».

**Качество:** журнал парсера, страница «Интеграции → Качество данных», предупреждение администратору при доле ошибок парсинга выше 20%, кнопка «Пересчитать из сырых данных». Тесты парсеров на фикстурах: нормальный ответ, с null, с ошибкой, с неизвестными полями.

# СТРАНИЦЫ И ПАТТЕРН СПИСКОВ

Разделы: Дашборд, Клиенты, Объекты, Оборудование, Аварии, Заявки, Задачи, Сотрудники, Роли и права, Журнал действий, Интеграции, Настройки, Профиль.

**Единый шаблон списка:** заголовок, счётчик, «Добавить», «Импорт», «Экспорт» → кликабельные KPI-карточки (клик применяет фильтр) → панель фильтров (поиск, чипы, «Сбросить», сохранённые представления, **фильтры в URL**) → таблица → подвал «Показано N из M». Клик по строке открывает страницу-карточку, не модалку.

**Фильтр по провайдеру (мультивыбор, значения из `providers`) и колонка «Провайдер» с бейджем есть на Клиентах, Объектах, Оборудовании, Авариях, Заявках и Дашборде;** дополнительно фильтр по аккаунту провайдера. Для клиента срабатывает, если хотя бы один его объект у выбранного провайдера.

- **Клиенты.** KPI: всего, в порядке, внимание, проблемы, без объектов, новые за месяц, разбивка по провайдерам. Фильтры: статус, провайдер, город, ответственный, теги, «нет данных N часов». Колонки: клиент, статус, провайдеры, объектов, мощность, открытые аварии, ответственный, активность.
- **Объекты.** KPI: всего, в норме, внимание, проблемы, нет связи, суммарная мощность, текущая генерация, непривязанные. Фильтры: статус, провайдер, тип, схема подключения, страна, клиент, привязан или нет.
- **Оборудование.** KPI: всего, в сети, предупреждения, аварии, нет связи, по типам. Фильтры: тип, модель, статус, провайдер, объект, клиент. Поиск по серийному номеру.
- **Аварии.** KPI: открытые, failure, влияние на безопасность, за 24 ч, без заявки. Фильтры: уровень, влияние, статус, период, провайдер. Кнопка «Создать заявку» (одна авария, одна заявка).
- **Заявки, Задачи:** тот же шаблон со связями на клиента, объект, оборудование, аварию.

# КАРТОЧКИ И ССЫЛКИ

**Любое упоминание клиента, объекта, оборудования, аварии, заявки или сотрудника в интерфейсе (таблицы, дашборд, уведомления, журнал) это ссылка на карточку.** Бейдж провайдера ведёт в отфильтрованный список.
- **Клиент:** шапка (имя, статус, контакты, ответственный, быстрые действия); вкладки Обзор (показатели, блок проблем, заметки), Объекты (с провайдером), Оборудование, Заявки, Задачи, Документы, История.
- **Объект:** шапка (статус, адрес, клиент, провайдер, тип, мощность, часовой пояс, мини-карта); блок «Сейчас» (генерация, потребление, сеть, SOC, время обновления); график день, месяц, год из нашей БД; вкладки Оборудование (дерево по parent), Аварии, Заявки, Документы, История.
- **Оборудование:** шапка (серийный номер, модель, тип, статус, ссылки на объект и клиента, провайдер, время данных); вкладки Параметры (динамическая таблица с поиском, блок «Нераспознанные»), История (выбор параметров, график), Аварии (код, причина, решение, уровень, влияние), Настройки (чтение, если поддерживается), Заявки, Обслуживание, Документы.

# УПРАВЛЕНИЕ ОБОРУДОВАНИЕМ

Только при capabilities.sendCommands и с разрешением «Управление оборудованием». Перед отправкой читаются текущие настройки, диалог «было → станет» с подтверждением. Команды асинхронны: опрос результата до финального статуса или таймаута, понятные сообщения по кодам ошибок. Каждая команда пишется в `command_orders` и журнал. Серверная валидация диапазонов, формата времени, обязательных пар параметров и лимитов относительно номинальной мощности (неверная команда может повредить оборудование или нарушить условия подключения к сети). Сырые протокольные команды (Modbus) в интерфейс не выводить.

# АДАПТЕР DEYE (реализовать полностью)

База: `https://eu1-developer.deyecloud.com/v1.0` (регион настраивается). Все эндпоинты POST/JSON, кроме `GET /order/{orderId}`. Заголовок `authorization: Bearer {token}`. Проверяй `success`, пиши `requestId` в лог.
- **Токен:** `POST /account/token?appId=` с appSecret, password (SHA-256), один из email, username, mobile+countryCode; companyId опционально (без него личный аккаунт). accessToken уже содержит «Bearer », не дублируй. Срок около 60 дней, эндпоинта refresh нет, запрашивай заново. `/account/info` возвращает организации.
- **Станции:** `/station/list` (size ≤200), `/station/listWithDevice` (≤50), `/station/detail`, `/station/device` (≤10 станций), `/station/latest`, `/station/history` (granularity 1 кадры, 2 дни ≤31, 3 месяцы ≤12, 4 годы), `/station/history/power` (секунды, ≤12 мес.), `/station/alertList` (≤180 дн.), `/station/create` (валюта ISO 4217, пояс IANA, страна ISO 3166; обязательны name, locationAddress, locationLat/Lng, installedCapacity, currency, gridInterconnectionType, region). Изменить или удалить станцию через API нельзя, валидируй до создания.
- **Устройства:** `/device/list` (бизнес, ≤200), `/device/latest` (≤10 SN, dataList key/value/unit, значения строками), `/device/measurePoints`, `/device/history`, `/device/historyRaw` (≤5 суток), `/device/alertList` (≤30 суток), `/device/register` (stationId, gatewaySn, deviceSn; ошибка «no upload records» значит проверить SN и сначала настроить Wi-Fi логгера), `/device/addLogger` и `/deleteLogger` (бизнес, ≤10).
- **Настройки (чтение):** `/config/battery`, `/config/system`, `/config/tou`.
- **Команды:** `/order/sys/workMode/update`, `/energyPattern/update`, `/power/update` (MAX_SELL_POWER, MAX_SOLAR_POWER, ZERO_EXPORT_POWER), `/solarSell/control`, `/tou/switch`, `/tou/update` (6 интервалов по порядку, HH:mm кратно 5 мин, дни капсом), `/order/battery/modeControl`, `/battery/parameter/update` (поле в API с опечаткой `paramterType`), `/battery/type/update`, `/order/smartload/update` (пары onVoltage/offVoltage и onSOC/offSOC вместе), `/order/gridPeakShaving/control`, `/order/sys/limitControl`, `/strategy/dynamicControl` (+`/read`, `/readResult`). `/order/customControl` (сырой Modbus) не выводить.
- **Результат команды:** статус 0 ожидает, 100 отправляется, 300 обновление, 400 прервано, 500 ошибка, **666 успех**; ошибки: 501 конфликт команд, 502 неверный тип продукта, 505 системная, 510 разбор, 511 версия, 530 команда не выполнена, 570–573 прошивка и взаимодействие.
- **Маппинг:** станция type (HOUSE_ROOF, COMMERCIAL_ROOF, INDUSTRIAL_ROOF, GROUND), gridInterconnectionType → grid_mode, connectionStatus (NORMAL, PARTIAL_OFFLINE, ALL_OFFLINE, NO_DEVICE); startOperatingTime приходит числом или датой, поддержи оба. Устройство: deviceType → таблица типов, productId → модель (0_5412_1 трёхфазный HV гибрид, 0_5411_1 трёхфазный LV гибрид, 0_5407_1 однофазный гибрид), parentId → топология. Авария: level 0 notice, 1 warning, 2 failure; impact 0 none, 1 production, 2 safety, 3 both; status 1 открыта, 0 закрыта; времена в секундах.
- **Неоднозначности документации (проверить на реальных ответах, коэффициенты вынести в `unit_rules`):** единицы installedCapacity и generationPower не указаны (вероятно кВт и Вт); смысл и знак gridPower, wirePower, purchasePower не определены; статус устройства описан двумя нумерациями: `deviceState` (1 онлайн, 2 авария, 3 офлайн) и `connectStatus` (0 офлайн, 1 онлайн, 2 авария), парсер определяет по пришедшему полю, оба случая под тестом; много null и разнотипные поля.
