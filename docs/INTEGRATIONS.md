# Облачные интеграции и ключи

Аккаунт Deye принадлежит интеграции. Его создаёт администратор через `POST /api/deye/accounts/`. Данные приложения, логин и хеш пароля хранятся зашифрованными в `vendor_accounts.fields_encrypted`. Ключ шифрования передаётся серверу отдельно. Поле `base_url` определяет регион API аккаунта. Последовательность подключения с проверкой входа и импортом описана в [сценарии Deye](BUSINESS_LOGIC.md).

## Каталог и измерения

| Что нужно получить | Где посмотреть |
|---|---|
| Состояние аккаунтов интеграций | `GET /api/crm/integrations/accounts` |
| Обновить каталог станций аккаунта | `POST /api/crm/integrations/accounts/{id}/sync`. Фоновый цикл при включённой интеграции выполняется каждые 3 минуты. |
| Посмотреть локальный каталог объектов | `GET /api/crm/sites` |
| Опросить импортированные инверторы | `POST /api/deye/sync/`. Интервал фонового опроса задаёт `DEYE_POLL_INTERVAL`. |

Знак мощности батареи и сети учитывается при переводе ответа облака в формат модема. При импорте можно задать `invert_battery` и `invert_grid`. [Преобразование показаний](../pkg/deye/mapper.go)

## Хранение и смена ключа

До обновления экземпляра с существующими облачными аккаунтами создайте ключ
(`openssl rand -base64 32`) и сохраните его в защищённом `.env` или менеджере
секретов как `PROVIDER_MASTER_KEY`. Укажите `PROVIDER_KEY_VERSION=1`. При старте
приложение переносит старые учётные данные в AES-256-GCM и очищает прежние поля.
Без ключа можно использовать локальный мониторинг и демо на базе без облачных
аккаунтов. Старые резервные копии, сделанные до миграции, нужно защищать отдельно.

Для ротации остановите приложение и отдельные процессы-воркеры. Перенесите
текущую пару в `PROVIDER_PREVIOUS_MASTER_KEY` и `PROVIDER_PREVIOUS_KEY_VERSION`,
задайте новый случайный ключ и новую версию. После успешного запуска и переноса
удалите предыдущую пару из рабочей конфигурации. Для восстановления старой
резервной копии потребуется ключ её версии.

## Подключение адаптера

Реестр в `providers` выбирает адаптер по столбцу `adapter`. Реальный адаптер
каталога реализует `SiteCatalogAdapter.FetchSites`, возвращает `CatalogSite`
и регистрируется в `server.NewServices`. Новые внешние поля нормализуйте внутри
адаптера и проверяйте на обезличенных фикстурах. Eybond работает на демоданных и
не требует ключей. Реальный транспорт можно подключить после получения документации.

## ValueClouds

После обновления сервер применит миграцию `008_valueclouds`. В разделе
«Интеграции» администратор выбирает «Подключить ValueClouds», указывает название,
логин и пароль. Каталог обновляется сразу после сохранения и затем каждые три
минуты. Кнопка «Изменить» позволяет заменить учётные данные; пустые поля логина и
пароля при редактировании сохраняют прежние значения.

Клиент использует `https://api.valueclouds.com`: вход
`POST /ppr/web/login/login` с SHA-1 пароля, `project=IOT`, сессионные `token`,
`secret` и заголовок `Auth`. Подпись — HMAC-SHA256 пути запроса с `secret` из
ответа входа, как в публичном клиенте ValueClouds. Заголовок `Auth` обновляется
из ответов; при истечении сессии выполняется один повторный вход. Логин и хеш
пароля хранятся в существующем зашифрованном хранилище, сессия — только в памяти.
Токены и секреты из cURL-примеров не являются конфигурацией приложения.

Каталог объединяет облачные проекты и устройства. Прибор без `pid` отображается
отдельным объектом. Объекты доступны через общий список `/api/crm/sites`;
дашборды станции и инвертора используют отдельные маршруты
`/api/crm/valueclouds/sites/{id}/...`. Идентификатор устройства включает
коллектор `pn`, `sn` и адрес; перед передачей в URL его нужно кодировать.

| Действие | API (admin) |
|---|---|
| Создать / посмотреть аккаунты | `POST /api/valueclouds/accounts`, `GET /api/valueclouds/accounts` |
| Изменить / отключить аккаунт | `PATCH /api/valueclouds/accounts/{id}`, в том числе `is_active=false` |
| Проверить вход | `POST /api/valueclouds/accounts/{id}/test` |
| Список устройств с ключами импорта | `GET /api/valueclouds/accounts/{id}/devices` |
| Импортировать в постоянный мониторинг клиента | `POST /api/valueclouds/accounts/{id}/import` с `device_key`, `client`, необязательными `name` и `site` |
| Обновить каталог | `POST /api/crm/integrations/accounts/{id}/sync` |

Суточная история содержит мощность PV, сети, нагрузки, заряда и разряда.
Графики месяца и года содержат энергию; режим «всё время» собирается по годам
с момента добавления устройства в облако. Произвольная история напряжения,
тока и регистров через DCS не предоставляется; эти значения доступны среди
текущих показателей. Пропуски остаются пропусками. Мощность нормализуется в Вт,
энергия — в кВт·ч. Направление текущей мощности сохраняется из ответа API;
потоки истории сети и батареи вычисляются из раздельных покупки/продажи и
заряда/разряда. Для объектов пока используется `Asia/Bishkek`: поле `timezone`
в полученных записях приборов равно нулю и не подтверждает их часовой пояс.

`VALUECLOUDS_ENABLED=false` отключает фоновую синхронизацию ValueClouds независимо
от `DEYE_ENABLED`. Сборщик импортированных модемов использует общий интервал
`DEYE_POLL_INTERVAL` и облачный таймаут `DEYE_OFFLINE_TIMEOUT`; показания старше
10 минут или из будущего не обновляют статус связи. Отключить конкретный
аккаунт можно через `is_active`, провайдера — через настройки провайдеров CRM.
Старые демообъекты Eybond остаются отдельным провайдером.

Для автоматического подключения из окружения задайте `VALUECLOUDS_USERNAME`
и `VALUECLOUDS_PASSWORD_SHA1` (готовый SHA-1 из тела запроса `/login/login`).
При следующем запуске сервер создаст зашифрованный аккаунт один раз; последующие
изменения аккаунта через CRM сохраняются. API создания/редактирования также
принимает `password_sha1` вместо `password`. Передавать оба поля одновременно
нельзя. Исходный пароль в форме CRM по-прежнему хешируется сервером.

Для рефреша используется повторный `POST /ppr/web/login/login` с сохранённым
SHA-1. При кодах истечения сессии `4`, `35`, `303` или HTTP 401 клиент получает
новые `token`, `secret`, `Auth` и один раз повторяет исходный запрос с новой
подписью. Циклических повторов при неверных учётных данных нет.

Карточка инвертора ValueClouds читает все пять источников: потоки энергии,
последние измерения по группам, активные параметры с временем обновления,
паспорт устройства с вложенным `collectorDTO`, а также порядок полей.
Типизированные методы и ответы находятся в `pkg/valueclouds/measurements.go`.
UID для запросов параметров берётся из ответа входа, без привязки к конкретному
пользователю. В карточке показаны физический серийный номер, коллектор, адрес,
тип логгера, прошивка и смещение часового пояса из `singleDeviceInfo`.

Группы `gd_`, `pv_`, `bt_`, `bc_`, `sy_` сохраняются при отображении, включая
параметры с нестандартными идентификаторами. Блок «Активные параметры устройства»
показывает список `queryDevicePars` с его порядком и временем; полный набор
`querySPDeviceLastData` остаётся в блоках сети, нагрузки, PV и батареи, а также
в раскрываемом списке всех показателей. Параметры, скрытые в настройках портала
производителя, доступны в полном списке. Порядок доступных рядов графика
следует `queryDeviceChartsFields`; единицы берутся из фактического измерения.
